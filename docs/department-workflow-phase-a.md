# Department Workflow — Phase A Design (migration-shape only)

> **Status**: design, awaiting owner review.
> **Author**: generated by Claude Code on 2026-10-16 for ai.shantaztf@gmail.com.
> **Scope**: Phase A features only — handover, acceptance, 2h timeout/HOLD, per-department durations, overrun narration. Does **not** cover Phase B (checklists / pending items / signature pad persistence) or Phase C (reports / attachments / rating) — those will get their own documents.
> **Guarantee**: this document describes shape only. No files in `src/`, no migrations, no RLS, no deployment have been or will be changed until you approve this document.

---

## 1. Executive summary

Phase A adds a department-ownership state machine on top of the existing `machine_log.stage` field without changing its values. Each stage becomes a department; moving a machine between stages becomes a two-step **Finish & Transfer → Accept** flow with a stored handover record, a receiver re-authentication step, a signature capture, and a HOLD flag computed on UI render (no cron).

**What stays identical:**

- `MACHINE_STAGES = ["BOM Issued", "Assembly", "Mechanical", "Electrical", "Trial", "Ready"]` — unchanged.
- BOM lifecycle, Rack view, Issue → Rack / Direct Production routing, stock reversal, Remove From Rack — unchanged.
- `handleStartProduction` (BOM Issued → Assembly) — unchanged in shape; it now also writes `current_department = 'Assembly'` and `department_entered_at = now()`.
- All existing audit events (`machine_created`, `machine_stage`, `machine_completed`, `production_started`) — unchanged.
- Permissions model (`canDo`) — unchanged; new permissions added additively.

**What's new:**

- Table `handover_events` — audit of every Finish & Transfer / Accept.
- Columns on `machine_log`: `current_department`, `department_entered_at`, `pending_handover_id`.
- JSONB field on `settings`: `department_workflow.{dept_durations, accept_timeout_minutes}`.
- Table `employee_signatures` — one row per user; stores the signature SVG and the hashed proof token.
- UI changes isolated to Machine card + Settings page + a small accept-pending list at the top of Machine Tracker.
- Audit event types: `handover_sent`, `handover_accepted`, `handover_overrun_narrated`, `signature_registered`.

---

## 2. Confirmed design decisions (locked by owner)

1. **Scope**: Phase A only. Document first, no code.
2. **Who can accept**: an authenticated user who (a) is currently signed in, (b) has the receiving department's role (via `canDo("machines", "accept-<Dept>")` — see §6), AND (c) completes a re-authentication step at accept time (password or password-less OTP via Supabase Auth) that re-attaches their stored signature SVG.
3. **HOLD detection**: computed on UI render only in Phase A. A handover is "overdue / HOLD" when `now_IST - sent_at > accept_timeout_minutes`. No cron, no scheduled Edge Function, no stored `held_at`. Phase B may add server-side flagging; Phase A keeps infrastructure flat.

## 3. Database shape

### 3.1 New table `public.handover_events`

```sql
-- Migration 021 (proposed)
CREATE TABLE IF NOT EXISTS public.handover_events (
  id                   bigserial       PRIMARY KEY,
  machine_id           bigint          NOT NULL
                                       REFERENCES public.machine_log(id)
                                       ON DELETE CASCADE,
  bom_key              text            NOT NULL,                       -- denormalized for reports after BOM delete
  serial_no            text,                                           -- denormalized
  from_department      text            NOT NULL CHECK (from_department IN
                                        ('BOM Issued','Assembly','Mechanical','Electrical','Trial')),
  to_department        text            NOT NULL CHECK (to_department IN
                                        ('Assembly','Mechanical','Electrical','Trial','Ready')),

  -- SEND side
  sent_by              uuid            NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT,
  sent_by_signature_id bigint          REFERENCES public.employee_signatures(id),  -- snapshot pointer
  sent_at              timestamptz     NOT NULL DEFAULT now(),
  expected_duration_minutes integer    NOT NULL,     -- was configured for from_department at send time
  actual_duration_minutes   integer    NOT NULL,     -- now() - department_entered_at at send time
  overrun_minutes      integer         GENERATED ALWAYS AS
                                        (GREATEST(0, actual_duration_minutes - expected_duration_minutes))
                                        STORED,
  overrun_narration    text,                        -- required by UI when overrun_minutes > 0; enforced below

  -- ACCEPT side  (nullable until accepted)
  accepted_by          uuid            REFERENCES auth.users(id) ON DELETE RESTRICT,
  accepted_by_signature_id bigint      REFERENCES public.employee_signatures(id),
  accepted_at          timestamptz,

  -- Status is a simple enum. 'held' never written server-side in Phase A — HOLD is a derived UI state.
  status               text            NOT NULL DEFAULT 'pending'
                                       CHECK (status IN ('pending','accepted','cancelled')),

  cancelled_at         timestamptz,
  cancellation_reason  text,

  accept_timeout_minutes integer       NOT NULL,     -- snapshot of settings.accept_timeout_minutes at send time
  created_at           timestamptz     NOT NULL DEFAULT now(),

  -- Enforcement
  CONSTRAINT handover_dept_different       CHECK (from_department IS DISTINCT FROM to_department),
  CONSTRAINT handover_narration_when_over  CHECK (overrun_minutes = 0 OR
                                                  (overrun_narration IS NOT NULL
                                                   AND length(trim(overrun_narration)) > 0)),
  CONSTRAINT handover_accept_fields_pair   CHECK (
    (status = 'accepted' AND accepted_by IS NOT NULL AND accepted_at IS NOT NULL)
     OR
    (status <> 'accepted' AND accepted_by IS NULL AND accepted_at IS NULL)
  ),
  CONSTRAINT handover_cancel_fields_pair   CHECK (
    (status = 'cancelled' AND cancelled_at IS NOT NULL)
     OR
    (status <> 'cancelled' AND cancelled_at IS NULL)
  )
);

CREATE INDEX IF NOT EXISTS handover_events_machine_idx ON public.handover_events (machine_id);
CREATE INDEX IF NOT EXISTS handover_events_status_idx  ON public.handover_events (status);
CREATE INDEX IF NOT EXISTS handover_events_pending_timeout_idx
  ON public.handover_events (sent_at)
  WHERE status = 'pending';   -- used by the pending-handover query in Machine Tracker
```

Design notes:

- `sent_by` / `accepted_by` reference `auth.users(id)` directly — same pattern as `audit_log` (migration 004 / 010). RESTRICT on delete so handover history isn't quietly dropped when a user is removed.
- `expected_duration_minutes` and `actual_duration_minutes` are stored at send time, not computed later. If the admin changes a department's configured duration tomorrow, old handovers still show against the duration that was in effect when they happened. **Historical correctness over current config.**
- `accept_timeout_minutes` is similarly snapshot. HOLD detection reads this stored value, not the current setting.
- `overrun_minutes` is a Postgres generated column so reports don't need to re-compute.
- `overrun_narration` is enforced at the DB layer via CHECK constraint, not just UI. A direct `INSERT` without narration where `overrun_minutes > 0` is rejected.
- `status = 'held'` is **not** a stored state in Phase A. See §7.
- `cancelled` state is reserved for future (sender revokes a pending handover before accept). Phase A UI will **not** expose cancel; the state is in the schema so adding it in Phase B doesn't need a migration.

### 3.2 New columns on `public.machine_log`

```sql
-- Migration 021 (continued)
ALTER TABLE public.machine_log
  ADD COLUMN IF NOT EXISTS current_department      text,       -- mirrors stage; nullable for legacy rows
  ADD COLUMN IF NOT EXISTS department_entered_at   timestamptz,
  ADD COLUMN IF NOT EXISTS pending_handover_id     bigint
                                                   REFERENCES public.handover_events(id) ON DELETE SET NULL;

-- Backfill for existing rows: adopt current stage as current_department, and set
-- department_entered_at to the newest history entry's date (or created_date).
-- This runs ONCE at migration apply time. Idempotent via WHERE clause.
UPDATE public.machine_log
   SET current_department    = stage,
       department_entered_at = COALESCE(
         (SELECT (h->>'date')::timestamptz
            FROM jsonb_array_elements(history) h
           ORDER BY (h->>'date')::timestamptz DESC
           LIMIT 1),
         created_date::timestamptz,
         created_at
       )
 WHERE current_department IS NULL;

CREATE INDEX IF NOT EXISTS machine_log_pending_handover_idx
  ON public.machine_log (pending_handover_id) WHERE pending_handover_id IS NOT NULL;
```

Design notes:

- `current_department` is deliberately redundant with `stage`. During Phase A, both are maintained; the app continues to display `stage`. The redundancy allows a Phase B refactor to make department ownership explicit without a second migration.
- `pending_handover_id` is nullable: a machine has either no handover in flight (null) or exactly one in flight. UI uses this to render "Accept" button + HOLD badge without a per-render query against the whole `handover_events` table.
- Backfill is **additive**. No existing row is deleted or changed in a user-visible way.

### 3.3 New JSONB on `public.settings`

```sql
-- Migration 022 (proposed) — pure additive, no schema change
-- settings is a single-row jsonb-backed table; this doc just names the new keys.
--
-- Expected structure once applied by the Settings UI:
--   settings.department_workflow = {
--     "dept_durations": {
--       "Assembly":   { "minutes": 2880 },        -- 2 days
--       "Mechanical": { "minutes": 2880 },        -- 2 days
--       "Electrical": { "minutes": 1440 },        -- 1 day
--       "Trial":      { "minutes":  480 }         -- 8 hours
--     },
--     "accept_timeout_minutes": 120               -- 2 hours
--   }
--
-- No ALTER TABLE needed. Owner-chosen defaults will be seeded by the Settings
-- page's first save; the UI falls back to the above constants when
-- settings.department_workflow is absent.
```

Design notes:

- Zero schema risk. If `settings_updated` audit event fires with new keys, nothing breaks.
- Falls back to hard-coded safe defaults in the client if the key is missing — matches the pattern already used for `settings.po` (PO template).
- `minutes` chosen as the single unit of time (no mixed hours/days in storage) so arithmetic is boring. UI renders as "2 days" / "8 hours" based on magnitude.

### 3.4 New table `public.employee_signatures`

```sql
-- Migration 021 (continued)
CREATE TABLE IF NOT EXISTS public.employee_signatures (
  id            bigserial       PRIMARY KEY,
  user_id       uuid            NOT NULL UNIQUE REFERENCES auth.users(id) ON DELETE CASCADE,
  signature_svg text            NOT NULL,     -- captured once; replaceable only by same user
  created_at    timestamptz     NOT NULL DEFAULT now(),
  updated_at    timestamptz     NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS employee_signatures_user_idx ON public.employee_signatures (user_id);
```

Design notes:

- **One signature per user**, enforced by `UNIQUE user_id`. Replacing a signature requires authenticated re-draw by the same user (not an admin override — admins have other audit trails).
- Phase A stores the SVG; Phase B may add hashing, re-auth tokens, or signed-URL exports. Phase A keeps it simple.
- `signature_svg` is text (a serialized SVG). Not image bytes. Keeps rows small, avoids Storage buckets, and the signature itself is low-sensitivity.
- No PII beyond the user-drawn shape. Not legally binding on its own — see §6 for the authentication requirement.

### 3.5 Four new audit event types

Added to `audit_log` (existing table, no schema change). Regression suite will be extended:

| Event type | When | Payload shape |
|---|---|---|
| `handover_sent` | On successful `handover_events` insert | `{ machine_id, from, to, expected_min, actual_min, overrun_min, narration_present }` |
| `handover_accepted` | On accept — after re-auth passes | `{ handover_id, machine_id, from, to, time_to_accept_min, was_overdue }` |
| `handover_overrun_narrated` | Separately logs narration text so audit_log is the queryable source | `{ handover_id, narration }` |
| `signature_registered` | First-time signature capture or replacement | `{ user_id, replacement: bool }` |

## 4. Backward compatibility

### What breaks if migrations are applied?

- Nothing in the current app. The migration adds columns and tables. No existing column is renamed, retyped, or dropped. No RLS policy on existing tables is modified in this migration.

### What happens if migrations are **not** yet applied (code shipped first)?

- The handover store will see a 42703 (`column does not exist`) or `PGRST204` error and fall back exactly like `posStore` and `itemsStore` already do (`isMissingColumnError` helper, strip-and-retry). The Finish & Transfer button will show "⚠ Enable with migration 021" instead of operating. Rack / BOM / Stock / existing stages continue to work.

### What happens if code is **not** yet shipped (migrations applied first)?

- The existing app continues to work. New columns default to NULL. The backfill `UPDATE` seeds `current_department = stage` and `department_entered_at` from history — no visible change.

### What happens if migrations roll back (see §9)?

- Rollback drops the three new columns on `machine_log` and the two new tables. The current app never read those, so operation continues as before the migration. Only cost is loss of handover history captured between apply and rollback — rolled-back handover rows are gone, but original `machine_log.history` entries that mirrored them stay (the Finish-Transfer flow will also append to `machine_log.history` for backward-compatible reads).

## 5. Security + RLS

### 5.1 Existing tables — no policy change

Phase A does not touch RLS on `machine_log`, `audit_log`, `settings`, `users`, `roles`, `vendors`, `items`, `purchase_orders`, `inward_log`, `outward_log`, `pending_log`, `bom_definitions`, `stock_movements`, `follow_ups`, `item_history`. Explicitly out of scope.

### 5.2 `handover_events` policies

```sql
ALTER TABLE public.handover_events ENABLE ROW LEVEL SECURITY;

-- Any authenticated user can SELECT (needed for Audit Trail / future reports).
-- Narrower per-dept filtering is a UI concern; RLS stays permissive-read to
-- avoid breaking Audit Trail's cross-dept view.
CREATE POLICY handover_events_select_authenticated
  ON public.handover_events
  FOR SELECT TO authenticated
  USING (true);

-- INSERT: only the sender is auth.uid() and only when the configured role
-- grants outward.bom. This mirrors how stage updates are gated today
-- (machines.updateStage). The receiving-dept check lives in UI, not RLS,
-- because roles aren't dept-tagged in the current schema.
CREATE POLICY handover_events_insert_sender
  ON public.handover_events
  FOR INSERT TO authenticated
  WITH CHECK (sent_by = auth.uid());

-- UPDATE for accept: only when auth.uid() matches the accepted_by we're
-- trying to write, and the row is still pending. No one else can mutate.
CREATE POLICY handover_events_accept
  ON public.handover_events
  FOR UPDATE TO authenticated
  USING (status = 'pending')
  WITH CHECK (
       (status = 'accepted' AND accepted_by = auth.uid())
    OR (status = 'cancelled' AND sent_by    = auth.uid())    -- only sender cancels (future)
  );

-- DELETE: forbidden. Handover history is append-only. CASCADE from
-- machine_log is the only legitimate deletion path.
-- (No policy grants DELETE — default-deny applies.)
```

### 5.3 `employee_signatures` policies

```sql
ALTER TABLE public.employee_signatures ENABLE ROW LEVEL SECURITY;

-- SELECT: a user can read their own signature. The handover flow attaches
-- the signature pointer, not the SVG itself, so other users don't need to
-- see signature contents.
CREATE POLICY signatures_select_self
  ON public.employee_signatures
  FOR SELECT TO authenticated
  USING (user_id = auth.uid());

-- INSERT: user can insert their own signature exactly once (UNIQUE user_id
-- enforces this at the schema layer; policy enforces identity).
CREATE POLICY signatures_insert_self
  ON public.employee_signatures
  FOR INSERT TO authenticated
  WITH CHECK (user_id = auth.uid());

-- UPDATE: user can replace their own signature.
CREATE POLICY signatures_update_self
  ON public.employee_signatures
  FOR UPDATE TO authenticated
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());

-- DELETE: forbidden (same reason as handover). Users don't delete signatures;
-- a replacement UPDATE suffices.
```

### 5.4 Re-authentication at accept time

Supabase Auth exposes `supabase.auth.signInWithPassword({ email, password })`. The accept flow will:

1. Prompt the receiver for their password in a modal.
2. Call `signInWithPassword({ email: currentUser.email, password })` on a **separate** client instance so a wrong password doesn't log the user out of their main session.
3. On success, read the stored signature SVG via a `SELECT ... FROM employee_signatures WHERE user_id = auth.uid()`.
4. If the user has no signature yet, open a one-time signature-pad modal; store with `INSERT`.
5. Call the handover `UPDATE` with `accepted_by = auth.uid()` and `accepted_by_signature_id = <id>`.

This satisfies the owner's requirement: *"a saved signature alone must not count as proof of authorization: require the correct employee to be authenticated when signing/finishing."*

### 5.5 New `canDo` permissions (added additively to the roles schema)

- `machines.finishTransfer` — can click Finish & Transfer. Default: Production role.
- `machines.accept` — can click Accept on a pending handover. Default: Production role.
- `machines.configDept` — can set per-department durations and accept-timeout in Settings. Default: Admin role, super_admin.

None of the existing permissions change meaning. Users who already have `machines.updateStage` continue to be able to update stages via the current UI *until* Phase A rolls out; after rollout, the dropdown is replaced by Finish & Transfer, and `machines.updateStage` becomes equivalent to `machines.finishTransfer`.

**Open question** (see §12): should existing `machines.updateStage` be auto-mapped to the two new permissions, or should Admins re-grant explicitly? Default proposal: auto-map at app boot in `resolveCanDo` so operators don't lose capability silently.

## 6. Timestamp logic

**Timezone**: Asia/Kolkata (IST, UTC+05:30) for all display.
**Storage**: UTC (`timestamptz`) in Postgres — never store wall-clock local time.
**Conversion**: `toLocaleString('en-IN', { timeZone: 'Asia/Kolkata' })` for display; `new Date(iso).getTime()` for arithmetic.

### Fields

- `handover_events.sent_at`: set by `DEFAULT now()` at insert. Server-authoritative.
- `handover_events.accepted_at`: set by server-side UPDATE in RLS-approved call. Not UI-set.
- `machine_log.department_entered_at`: set by Finish-Transfer success handler to the just-written `accepted_at` of the previous handover (i.e. "clock starts when I was accepted into this dept"). For the first-ever Assembly entry (BOM Issued → Assembly), set to the `created_date` of the start-production event.

### Elapsed-time definition (locked)

```
elapsed_in_current_dept(machine)
  = now() - machine.department_entered_at

overrun_in_current_dept(machine, config)
  = max(0, elapsed_in_current_dept - config.dept_durations[machine.current_department].minutes)
```

- No "paused" state. If an operator leaves for lunch, the clock still runs. Simpler audit, matches what the owner asked for.
- A machine moved back to a previous dept (future feature, not Phase A) would reset `department_entered_at`.

### HOLD definition (locked)

```
is_pending_handover(h)   = h.status = 'pending'
is_overdue(h, now)       = is_pending_handover(h)
                            AND (now - h.sent_at) > h.accept_timeout_minutes * 60s

held_minutes(h, now)     = is_overdue(h, now) ? (now - h.sent_at - accept_timeout_minutes*60) : 0
```

Phase A does **not** write `status = 'held'`. The row stays `pending`; UI computes `is_overdue` at render time. When the handover is finally accepted, `handover_accepted` audit event carries `was_overdue: boolean` so Reports can distinguish on-time vs late-accept without rescanning timestamps.

## 7. Timeout handling (Phase A — computed only)

- No `pg_cron`. No scheduled Edge Function. No background job in the client.
- The Machine Tracker page re-renders on React state changes and on route visits; each render computes `is_overdue(h, now)` for all pending handovers in the visible set.
- A `setInterval(() => forceReRender(), 60000)` tick inside the Machine Tracker page refreshes the HOLD badge every minute even when no other state changes. Negligible CPU, no network traffic.
- No notification/email in Phase A. If operations wants push alerts, Phase B adds a scheduled Edge Function that INSERTs an audit event `handover_held_notified` when `now - sent_at > timeout + 15min` and nothing has been accepted. Phase A UI is already visible to any operator who looks.

### Edge cases

1. **Clock drift**: `now()` in the client vs server. HOLD computation uses `Date.now()` on the client. In practice `sent_at` is set by Postgres `now()` (UTC); server clock trusted. If a client clock is wildly wrong, a HOLD may appear a few seconds early/late — acceptable in Phase A.
2. **Machine deleted while handover is pending**: `handover_events` cascades on `machine_log` delete. No orphans.
3. **User deleted while handover is pending**: `sent_by` / `accepted_by` are RESTRICT'd — the deletion of a user with pending handovers in flight will fail at the DB level. Admin workflow: force-cancel pending handovers before deactivating that user. (In Phase A the "cancel" UI isn't exposed, so Phase A admins would route this through SQL. Acceptable for Phase A; Phase B surfaces Cancel.)
4. **Two accepts race-conditioning**: not possible because `UPDATE ... WHERE status = 'pending'` is an atomic row-lock. Second accept gets zero rows affected and the UI shows "Already accepted by X".
5. **Narration bypass**: UI narration input could be bypassed by a malicious direct API call. The CHECK constraint `handover_narration_when_over` enforces this server-side.

## 9. Rollback plan

**Code rollback**: `git revert <phase-a-commit>` on `main`; Vercel re-builds from the previous commit. Users see the current stage-dropdown workflow return. Any in-flight handover rows persist in the DB until migration rollback.

**Migration rollback (manual, authored at same time as 021)**:

```sql
-- Migration 021_rollback.sql — apply ONLY when returning to pre-Phase-A code.
BEGIN;

ALTER TABLE public.machine_log
  DROP COLUMN IF EXISTS pending_handover_id,
  DROP COLUMN IF EXISTS department_entered_at,
  DROP COLUMN IF EXISTS current_department;

DROP TABLE IF EXISTS public.handover_events;
DROP TABLE IF EXISTS public.employee_signatures;

-- settings.department_workflow is JSON inside the single-row settings
-- payload. Rollback script leaves it there; it's just unused keys. Delete
-- explicitly if desired:
--   UPDATE public.settings SET value = value - 'department_workflow';

COMMIT;
```

**Rollback data safety**: dropping `handover_events` loses handover history captured during Phase A. The sender's finish and the receiver's accept were ALSO mirrored into `machine_log.history` (append-only JSON) with `{stage, date, note: "Finished → <Dept>", by: <email>}` entries, so `machine_log.history` remains a legible — if less structured — audit trail even after rollback.

**Rollback test plan** (before merging Phase A): a scratch Supabase project runs the forward migration, inserts a handover, accepts it, runs the rollback, verifies the existing BOM + Rack + Stage flows still work.

## 11. Risks identified (owner should weigh before approving)

| Risk | Severity | Mitigation |
|---|---|---|
| **Operators lose the current stage-dropdown muscle memory** | High (UX) | Pre-release training note; keep the current "Update Stage" shown as "Finish & Transfer" so the button is in the same place |
| **A user with no stored signature can't accept** | Medium | Phase A one-time signature-pad modal appears automatically on first accept attempt; no admin action needed |
| **Narration bypass via malicious direct API call** | Medium | CHECK constraint `handover_narration_when_over` on the DB |
| **HOLD invisible if nobody opens Machine Tracker** | Low in Phase A | Documented: Phase A is purely visual on-render; Phase B adds server-side flagging if operations wants push |
| **Backfill of `current_department` is wrong for rows mid-production** | Low | Backfill sets `current_department = stage`, which is the current working state — same information operators see today; no behavior change |
| **A user who re-authenticates with wrong password 100 times** | Low | Supabase Auth rate-limits password attempts; secondary client doesn't tie to session; wrong-password errors are inline |
| **Race: two users click Accept simultaneously** | Low | Single-row atomic UPDATE with `WHERE status='pending'`; losers see zero rows affected, UI reads refreshed state |
| **Narration text contains PII / confidential info** | Medium | Audit log row count-only in Customer Progress Report; narration never appears in customer-facing output (Phase C concern) |
| **Signature SVG size unbounded** | Low | UI canvas is 400×150 — serialized SVG max observed ~5 KB. No DB storage pressure |
| **Phase A ships without Phase B pending-items** | Medium (feature #6 deferred) | Clearly disclosed; Accept modal has a placeholder note "⏳ Pending-items check (Phase B)" so operators know it's coming |
| **Deployment lag between code and migration** | High if mis-sequenced | Deploy order fixed: `migration 021 first (safe additive) → code deploy second`. Rollback order is the reverse |

## 12. Open decisions that still need the owner

Items I would not decide unilaterally even in autonomous implementation mode. Flag them now:

1. **Default per-department durations.** Proposed: Assembly 2d, Mechanical 2d, Electrical 1d, Trial 8h. **Decide**: initial values; what for Ready and BOM Issued (likely N/A — Ready is terminal, BOM Issued is pre-production rack).

2. **Mapping of existing `machines.updateStage` permission.** Proposed: auto-grant `machines.finishTransfer` and `machines.accept` to anyone who currently has `machines.updateStage`, so operators don't lose capability at rollout. **Decide**: auto-map (default) OR require explicit regrant.

3. **Should the Accept modal require re-auth every single time, or once per session?** Proposed: every time (per feature #8). **Decide**: confirm, or soften to once-per-session for operational speed.

4. **Who can register / replace a signature?** Proposed: only the user themself. Admins cannot sign on another user's behalf. **Decide**: confirm, or allow admin-assist for signature-illiterate operators.

5. **Email/notification on HOLD?** Phase A says no. **Decide**: hold firm (Phase A has no email), or allow a tiny Supabase Function in Phase A that emails the department lead on first HOLD transition. Adds ~1 session of work.

6. **Ready department — is it a "department" for the handover model?** Proposed: Ready is a terminal state; Trial → Ready uses the same Finish & Transfer flow, but there's no further Finish-Transfer from Ready. Machine marked complete at the Trial accept.

7. **Operators moving a machine BACKWARDS (e.g., Electrical sends back to Mechanical for rework).** Phase A: not supported. Backward moves need an "ownership reset" and a different audit shape. Owner should confirm this is OK for Phase A.
